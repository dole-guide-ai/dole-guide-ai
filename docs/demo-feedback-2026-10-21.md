# 시연 개선 반영 (2026-10-21)

「실업급여 길잡이 프론트 시연플로우 개선사항」(2026-10-21, 13건)을 프론트와 모의 대본(`frontend/src/mocks`)에 반영한 내용과, 백엔드·AI가 이어서 맞춰야 할 것을 정리한다. 상세기획도 같은 날짜로 고쳤다(변경 이력 2026-10-21 행).

- 범위: 프론트 화면 + 모의 대본. 백엔드 API는 바꾸지 않았다.
- 테스트 순서는 같은 폴더의 「시연 개선 테스트 플로우」 pptx를 본다.

모의 전용 장치(백엔드가 대신해야 함):

- `lastAsk`: 직전 질문을 기억해 자유 입력을 그 질문의 답으로 처리하고, 대본에 없는 말에는 직전 질문을 다시 묻는다 (6번 PPT 점검). 실제로는 백엔드 대화 상태가 맡는다.
- `resetMockChat()`: 계정을 고를 때 모의 대화 상태를 비운다.
- `PATCH /forms/resume`의 자격 `acquired_date`를 `YYYY-MM-DD`로 검사한다(모의 핸들러). 백엔드도 같은 형식으로 받아야 한다.

## 3. 백엔드·AI에 전달할 것

### 3-1. SSE 계약 추가: `accepts_file` (2번)

```json
{ "event": "ask_user", "data": { "question_id": "resume.career_new", "text": "가장 최근에 일하신 곳부터 알려 주세요. 경력증명서가 있으면 파일로 올려 주세요.", "choices": ["파일 올릴게요", "고용24에서 불러올게요", "말로 할게요"], "accepts_file": true } }
```

- `ask_user.data.accepts_file?: boolean` — 이 질문이 서류·사진을 요청하면 `true`. 없거나 `false`면 프론트의 파일 버튼이 꺼진다.
- 진입 응답 `entry`(`EntryResult`)에도 같은 `accepts_file`을 둔다. 첫 질문이 서류를 요청하면(E7a 등) `true`.
- 이벤트 이름은 그대로라 `shared/sse-events.json`은 바뀌지 않는다. 백엔드 스키마에 필드를 넣은 뒤 `pnpm gen:api`로 `api.gen.ts`를 맞춘다. 지금 프론트는 `types/chat.types.ts`·`types/demo.types.ts`에 선택 필드로 먼저 두었다.
- 켜야 하는 질문: 경력(`career_new`), 자격(`license`), 1차 실업인정일(`procedure.first_date`), 다른 사이트 지원 캡처, 면접확인서, 판독 실패 뒤 다시 올리기.
- 선택지 문구는 `사진 올릴게요` 대신 `파일 올릴게요` (문서도 받음).

### 3-2. 응답 형식 규칙 (3번, 프롬프트)

- 목록은 줄마다 하나(`\n`). 프론트 말풍선은 줄바꿈을 그대로 보인다.
- 한 번에 한 가지만 요청한다.
- 말풍선이 여러 개면 마지막 말풍선에 "지금 할 일: …" 한 줄.
- 프롬프트 파일(`backend/app/agent/prompts/`)에 넣고 평가 세트에 사례를 더한다.

### 3-3. 칸 뜻 답하기·여러 정보 나눠 넣기 (7번, AI)

- "병역대체는 뭘 적는 거야?"처럼 칸 뜻을 물으면 답하고 직전 질문으로 돌아온다. `search_guide` 근거 줄을 붙인다.
- 한 문장에 여러 값(학교 기간과 직장 기간 등)이 있으면 칸마다 `form_update`를 따로 보낸다 (2-0.4 "말에 들어 있는 값을 모두 해당 칸에").

### 3-4. 직접 입력 저장 (8번)

- 패널 직접 입력은 `PATCH /forms/resume`로 `source = manual`, `본인 확인`으로 저장한다. 프론트가 보내는 값 형태:
  - 희망임금 `{ amount: number, unit: "monthly", negotiable: false }`
  - 목록 칸(기타자격 등) 문자열 배열, 경력 기간 `{ start: "YYYY-MM", end: "YYYY-MM" | null }`, 급여 숫자
  - 학력·졸업상태·고용형태·병역대체·재직여부·운전·차량은 고용24 선택지 글자 그대로
- **희망직종·희망지역·경력 직종은 직접 입력에서 뺐다.** 공통코드가 필요해서다. 대화에서 `lookup_code`로 맞추거나, 나중에 코드 검색 API(예: `GET /codes/occupations?q=`)를 만들면 프론트가 검색 선택 상자로 붙인다.

### 3-5. 불러오기 뒤 대화 잇기 (10번)

- 불러오기 결과를 넣은 뒤에는 꼭 다음 `ask_user`를 보낸다: 경력이 있으면 직급 → 주요 직무, 없으면 남은 꼭 묻는 항목.
- 직급 질문 선택지 `직급 말할게요 / 없었어요`. 자유 입력은 직전 질문의 답으로 처리한다(대화 상태에 직전 `question_id`를 둔다).

### 3-6. 같은 경력 중복 (11번)

- `detect_conflicts`·`fill_form`: 같은 회사·겹치는 기간이면 새 `item_id`를 만들지 말고 기존 `item_id`로 `set`(또는 같은 `item_id`로 `append`)한다.
- 프론트는 같은 `item_id`의 `append`를 합치도록 바꿨지만, 다른 `item_id`로 오면 두 건이 된다.

### 3-7. 최영수 2·3단계 (12번, 상세기획 1장 1.15)

- 단계 전환: E6 `교육 다 들었어요` → 이수 확인 → `education_done = true`, `stage = eligibility_application`(E5a, 패널 Q) → `방문 신청했어요` → `stage = eligibility_applied`(E5b, 1차 인정일 입력) → 날짜·안내문 → `stage = recognition`, `completed_rounds = 0`(E4a).
- 전환마다 `procedure` `form_update`로 `state`·`entry`(패널·진행바·제목·다음 할 일)·`derived`를 보낸다. 모의는 `moveStage`로 흉내 냈다.
- 1차 회차 점검(`GET /procedure/current-round/check`) 데이터가 필요하다. 1차 할 일은 **1차 교육**(60세 이상·장애인은 온라인이나 센터)이다.
- 알려진 차이: 지금 프론트 `RequirementCard`는 1차도 "활동 1건"으로 보인다. 1차는 "1차 교육"으로 보여야 하므로 점검 응답에 1차 교육 여부를 담을 필드가 필요하다(백엔드와 형식 합의 후 프론트 수정).

### 3-8. 활동 종류 (13번, 상세기획 2-2.5)

| 선택지 | 처리 | 증빙 |
| --- | --- | --- |
| 고용24 지원 내역 불러올게요 | 모의 불러오기 목록에서 고름 | 불필요 |
| 다른 사이트·이메일로 지원했어요 | 회사·날짜 묻고 지원 완료 화면 요청 (`accepts_file`) | 캡처 |
| 면접 봤어요 | 회사·날짜 묻고 면접확인서·명함 요청 (`accepts_file`) | 확인서 |
| 온라인 취업특강 들었어요 | 고용24 이수 확인 | 불필요 |
| 그 밖의 활동이에요 | 고용24 `구직활동 외 활동사항` 과정 14가지 중 고름 | 과정별 |

- 추천 뒤 선택지는 "지금 하러 감"과 "이미 한 것 기록"을 이름으로 나눈다: `고용24에서 지원하러 갈게요 / 온라인 취업특강 들으러 갈게요 / 이미 한 활동 기록할게요`.
