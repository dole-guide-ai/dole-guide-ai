## 1. 전체 진행 순서

**공부 → 설계 초안(가설) → 최소 버전 개발 + 첫 평가 → 실험으로 결정 확정 → 문서 완성 + PR**

- 처음 생각한 순서는 "공부 → 질문 결정 → 개발"이었는데, 질문을 개발 전에 **다 확정하지 않는다**는 점이 다릅니다.
- 이유: 이슈가 요구하는 건 "근거 있는 선택"입니다. 개발 전에 정해 버리면 근거가 "그럴 것 같아서"뿐입니다.
  **가설 → 측정 → 결정** 순서로 가야 근거를 숫자로 댈 수 있습니다.

| 단계 | 하는 일 | 끝났다는 기준 |
| --- | --- | --- |
| ① 공부 | LLM 기본, 프롬프트, 구조화 출력, LangGraph, RAG, 평가, 보안, 우리 코드 | 확인 질문에 내 말로 답할 수 있음 |
| ② 설계 초안 | 결정 질문 7개마다 대안 + 가설 | 설계 초안 문서 |
| ③ 최소 버전 | 가장 단순한 AI로 골든셋 채점 | 기준 점수 |
| ④ 실험 | 대안을 하나씩 바꿔 점수·비용·속도 비교 | 비교표 (= 선택의 근거) |
| ⑤ 완성 | 설계 문서 확정본 + PR | PR (머지는 안 함) |

## 2. 설계 문서는 어디에 둘까

**결정: 초안은 노션에서 쓰고, 확정본은 레포(`docs/ai/`)로 옮겨 PR에 포함한다.**

| 위치 | 좋은 점 |
| --- | --- |
| 레포 | 코드와 같이 리뷰받음, 설계와 코드가 같은 커밋으로 기록됨, AI 도구가 읽을 수 있음, 평가 결과와 한곳에 |
| 노션 | 쓰기 편함, 비개발자 팀원이 보기 쉬움, 댓글 달기 쉬움 |

- 이슈는 위치를 정하지 않았으므로 둘 다 가능합니다. 섞어 쓰면 두 장점을 다 가져갑니다.

## 3. 설계 초안은 무엇부터 정할까

**0단계: AI가 맡을 일의 범위부터.** 골든셋 4개 영역(절차 안내·서류 채우기·근거 답변·개인정보 보호)이 곧 할 일 목록입니다.

**결정 질문 순서: ② 판단은 누가? → ① 흐름 → ⑤ 답 형식 → ④ 근거 찾기 → ③ 모델 → ⑥ 사진 → ⑦ 보안**

| 순서 | 질문 | 이 순서인 이유 |
| --- | --- | --- |
| 1 | ② 판단은 누가 | 모든 설계의 뼈대. 규칙 코드와 AI의 역할을 나눠야 흐름을 그릴 수 있음 |
| 2 | ① 흐름 | 역할이 정해지면 단계가 정해짐 |
| 3 | ⑤ 답 형식 | 단계 사이에 무엇을 주고받을지 |
| 4 | ④ 근거 찾기 | 자료가 조각 916개(약 2.4MB)라 통째로 못 넣음 → 검색 방식 선택 |
| 5 | ③ 모델 | 역할별로 필요한 능력이 다름 |
| 6 | ⑥ 사진 | 서류 채우기의 일부라 독립적으로 결정 가능 |
| 7 | ⑦ 보안 | 흐름이 정해져야 어디서 막을지 정함 |

질문 하나를 채우는 양식: **질문 · 대안 · 장단점 · 가설 · 검증 방법(골든셋 어느 영역, 어떤 지표)**

## 4. ③ 최소 버전 개발과 기준 점수

### 만든 흐름

`preprocess`(개인정보 가리기) → `load_context`(규칙 코드로 회차·필요 건수 계산) → `respond`(모델 한 번, JSON 답) → `apply_updates`(서류·활동 반영)

| 누가 | 하는 일 |
| --- | --- |
| 규칙 코드 (`app/rules/situation.py`) | 회차, 필요 활동 수, 인정 건수, 부족 건수, 대상기간, 활동 증빙 |
| AI (`app/agent/nodes/respond.py`) | 말 이해, 서류 값 뽑기, 답 쓰기 |

- 회차·건수 계산은 팀 규칙 함수(`rules/rounds.check_round`, `rules/periods`)에 이미 있었습니다. 다만 이 함수들은 DB에 저장된 회차를 읽어 계산해서, DB 없이 상태값만 있는 골든셋에 쓰려면 다리가 필요했습니다. 그래서 `situation.py`가 상태값에서 회차·대상기간을 뽑아 팀 함수에 넘깁니다. 계산은 규칙 코드가 한다는 결정 ②와 같은 방향입니다.
  - (2026-10-25 정정) 처음에는 "백엔드에 계산 함수가 없어 새로 만들었다"고 적었는데, 작업 브랜치가 팀 코드(#184, 10/23 머지)를 받기 전이라 잘못 본 것이었습니다. 7-2절에서 제 계산을 지우고 팀 함수로 바꿨습니다.
- 근거 검색, 사진 읽기, 최종 검사(verify)는 일부러 뺐습니다. **나중에 붙였을 때 효과를 재기 위한 기준선**이기 때문입니다.

## 5. 커밋·푸시·PR은 어디까지 올라가나

```
① 커밋 → ② 푸시 → ③ PR → (④ 머지)
```

| 단계 | 어디까지 | 다른 사람에게 영향 |
| --- | --- | --- |
| 커밋 | 내 컴퓨터에만 저장 | 없음 |
| 푸시 | GitHub의 **내 브랜치**(`feat/#176-ai-minsoo`) | develop·main·다른 브랜치는 그대로 |
| PR | develop에 합쳐 달라는 **요청** + 리뷰 | 리뷰·검사가 돌지만 아직 합쳐지지 않음 |
| 머지 | develop에 실제로 합쳐짐 | 이슈 조건이 "PR까지"라 하지 않음 |

- 실험할 때마다 커밋·푸시하면 "무엇을 바꿨더니 점수가 어떻게 됐다"가 기록으로 남습니다.

## 6. 보안 검토 지적과 수정

커밋 후 자동 보안 검토가 개인정보 가리기(마스킹)의 빈틈을 세 번 찾았고 모두 고쳤습니다.

| 지적 | 예 | 수정 |
| --- | --- | --- |
| 붙여 쓴 주민번호 | `6501011234567` | 구분자 없이 13자리도 가림 |
| 한글에 붙은 번호 | `계좌110-234-567890이에요` | 숫자 경계를 `\b`(단어 경계) 대신 "앞뒤가 숫자가 아님"으로 판단 |
| 점·공백 구분 | `010.1234.5678`, `1234 5678 1234 5678` | 구분자로 공백·점·하이픈 허용 |
| 띄운 하이픈 | `110 - 234 - 567890` | 숫자 사이 구분자를 3글자까지 허용 |

- 10자리 미만 숫자는 가리지 않습니다. 국내 계좌가 10~14자리이고, 짧은 숫자까지 가리면 날짜·금액이 잘못 가려지기 때문입니다.
- 배운 점: 정규식 `\b`는 한글도 "글자"로 보기 때문에, 한글에 붙은 숫자 앞에서는 경계가 생기지 않습니다.

## 7. ④ 실험은 무엇부터 할까

**결정: 프롬프트 → 근거 검색(RAG) → 사진(OCR) → 모델 비교**

| 판단 기준 | 질문 |
| --- | --- |
| 효과 | 몇 문항을 고칠 수 있나 |
| 비용 | 새로 만들 게 얼마나 많나 |
| 의존성 | 다른 실험 결과에 영향을 주나 |
| 측정 | 효과를 깔끔하게 잴 수 있나 |

- **프롬프트가 1번인 이유:** 실패의 대부분이 답 문구이고, 고치기 가장 싸며(한 번 실행에 약 5분), 모든 실험의 바탕이라 먼저 고정해야 다음 실험의 효과를 구분할 수 있습니다.
- **모델 비교가 마지막인 이유:** 설정값만 바꾸면 되지만, 프롬프트·검색이 정해진 뒤에 재야 공정합니다.
- **주의:** 시험 문제에 맞춰 답을 외우게 하면(예: "12월 22일을 말해라") 점수만 오르고 실력은 그대로입니다. "상황의 숫자는 답에 반드시 넣어라"처럼 **일반 원칙**으로 고쳐야 근거로 인정받습니다.
- **주의:** AI는 같은 질문에도 답이 조금씩 달라서, 2~3점 차이는 우연일 수 있습니다. 중요한 비교는 2번씩 돌려 흔들림 폭을 함께 적습니다.

## 7-1. 첫 실험 결과: 프롬프트 (2026-10-24)

비교한 세 가지 (모두 gpt-5.4-mini, 채점 gpt-4.1, 버전마다 2회 실행):

| 버전 | 바꾼 것 | 1회 | 2회 | 평균 | 흔들림 | 절차(38) | 문항당 토큰 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 기준 | 최소 버전 | 45% | 38% | 41.5% | 7점 | 6 / 5 | 1,764 |
| A | 프롬프트 v2: 숫자는 "N건"·"M월 D일"로 직접, 근거 줄, 거절 원칙, 결론부터 | 55% | 63% | 59% | 8점 | 13 / 18 | 2,444 |
| B | A + 규칙 코드가 출처 달린 사실 문장을 만들어 AI가 그대로 옮김 | 63% | 62% | **62.5%** | **1점** | **21 / 22** | 2,733 |

**결정: B 채택.**

- 기준 → A(+17.5점)는 흔들림보다 훨씬 커서 확실한 개선입니다. 지시문만 바꿔도 효과가 큽니다.
- A → B는 전체로는 +3.5점이라 흔들림 안입니다(우연일 수 있음). 하지만 **숫자·날짜를 말해야 하는 절차 영역이 확실히 좋아졌고**, **흔들림이 8점 → 1점**으로 줄었습니다.
- 행정 안내는 매번 같은 답을 주는 것이 중요하므로 안정성을 근거로 B를 고릅니다. 토큰은 12% 늘지만 문항당 약 300토큰이라 부담이 작습니다.
- 결정 ②(계산은 규칙 코드)를 **문장 단계까지** 적용한 것이 맞다는 근거입니다.

배운 점:

- **같은 코드도 점수가 7점 흔들린다.** 그래서 대안마다 2회씩 돌려 평균과 흔들림을 함께 봐야 합니다. 차이가 흔들림보다 작으면 "좋아졌다"고 말하지 않습니다.
- **문항에 맞춘 문구를 넣지 않는다.** "12월 22일을 말해라"가 아니라 "상황의 숫자는 답에 직접 써라" 같은 원칙만 넣어야 점수가 실력을 보여 줍니다.
- 비용 비교를 위해 골든셋 보고서에 모델 호출 수·토큰·시간 집계를 추가했습니다(판정 모델은 제외).

develop 최신화 (2026-10-24):

- develop을 합치니 필요 건수 계산이 팀의 활동 규칙 표(`data/rules/activities.json`)로 옮겨져 있어, 제 코드도 그 표를 읽게 바꿨습니다. 표에 없는 유형(반복수급자)은 "계산할 수 없으니 센터에 확인"으로 안내합니다(이전엔 "다 채웠어요"로 잘못 말할 수 있었음).
- 합친 뒤 골든셋 62%로 B와 같은 수준을 확인했습니다.
- develop에 팀원의 개인정보 가리기(`agent/input/pii.py`)와 회차 점검(`rules/rounds.py`)이 들어와 제 코드와 겹칩니다. 정리 대상입니다.
- 실험이 도는 중에는 develop을 합치지 않았습니다. 중간에 코드가 바뀌면 2회차 실행이 다른 코드로 돌아 비교가 오염되기 때문입니다.

## 7-2. 팀원 코드와 겹치는 부분 정리 (2026-10-24)

develop에 팀원이 만든 공용 코드가 들어와 제 코드와 겹쳤습니다. 같은 일을 두 곳에서 하면 규칙이 바뀔 때 한쪽만 고쳐지는 위험이 있어, 팀 코드를 쓰도록 바꿨습니다.

| 하는 일 | 바꾸기 전 (내 코드) | 바꾼 뒤 |
| --- | --- | --- |
| 개인정보 가리기 | `agent/masking.py`에 모든 패턴 | 팀 `agent/input/pii.py`(생년월일 검증·카드 Luhn 검사·외부 전송 차단)를 먼저 쓰고, **pii가 놓치는 경우만** 보강 |
| 회차 점검 (같은 날 1건, 기간 밖) | `situation.py`에 직접 계산 | 팀 `rules/rounds.py`의 `check_round` (허용 종류·누적 한도·주 단위까지 포함) |
| 활동 종류 이름·필요 증빙 | `situation.py`에 임시 표 | 팀 활동 규칙 표 `rules/activity_table.py` (`data/rules/activities.json`) |
| 같은 날 1건 사실 문장 | 날짜를 직접 세서 만듦 | 회차 점검의 경고 문구를 그대로 사용 |

pii.py가 놓쳐서 내 코드에 남긴 보강 (이전 보안 검토에서 막은 경우):

| 사례 | 예 |
| --- | --- |
| 주민번호 뒷자리만 말함 (골든셋 M-005) | "뒷자리는 1234567" |
| 점으로 구분한 주민번호 | 650101.1234567 |
| 구분자 없거나 공백·밑줄·슬래시·띄운 하이픈으로 쓴 계좌·카드 번호 | 11023456789012, 110 - 234 - 567890 |
| 자기소개 말투의 이름 | "제 이름은 홍길동이에요" |

## 7-3. 두 번째 실험 결과: 근거 검색(RAG) (2026-10-24)

기준은 직전 버전(69.5%). 모두 gpt-5.4-mini, 채점 gpt-4.1, 임베딩 text-embedding-3-small, 대안마다 2회.

| 버전 | 방식 | 1회 | 2회 | 평균 | 기준 대비 | 문항당 토큰 | 평균 시간 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 기준 | 검색 없음 | 68% | 71% | **69.5%** | — | 2,757 | 1.4초 |
| D | 활동 규칙 표 → 내 유형·회차에 맞춘 규칙 카드 (검색 없음) | 68% | 69% | 68.5% | -1 (흔들림 안) | 3,983 (+44%) | 1.4초 |

**결정: v1은 검색(RAG)을 쓰지 않는다 (RETRIEVAL_MODE=none). 규칙 카드도 기본값은 끈다.**

왜 RAG가 오히려 나빠졌나:

1. **우리 자료에 필요한 규정이 거의 없다.** 남은 실패는 "증빙은 뭘 내나", "학원도 인정되나" 같은 실업인정 세부 규정인데, 지식 자료(1350 FAQ 94개 + 고용24 정책 822개)에는 이런 내용이 드물고 대학 일자리센터처럼 상관없는 정책이 많다. 검색하면 비슷해 보이는 엉뚱한 글이 들어온다.
2. **모든 질문에 참고 자료를 붙이면 AI가 산만해진다.** 키워드 검색에서 꾸준히 나빠진 7문항 중에는 경력 날짜 뽑기(F-001·F-002)처럼 규정과 상관없는 서류 질문이 있었다. 필요 없는 글 4개가 매번 들어가 정작 할 일(값 뽑기)을 놓쳤다.
3. 비용도 늘었다. 토큰 +45~51%, 벡터는 질문 임베딩 때문에 응답이 0.6초 느려졌다.

규칙 카드(D)에서 알게 된 것:

- **딱 증빙 질문 3개가 좋아졌다**(P-024 취업활동증명서, P-025 보낸편지함, P-033 캡처). 정리된 규칙 표가 검색보다 정확하다는 뜻이다.
- 하지만 서류·사진 질문 3개가 나빠져 전체로는 비슷했고(흔들림 안), 토큰은 44% 늘었다. 2번과 같은 원인(필요 없을 때도 붙음)이다.

→ 다음 개선 방향: **질문 종류를 먼저 가려(의도 분류), 규정 질문일 때만 규칙 카드를 붙이기.** 설계 초안 ① 흐름의 "의도 분류 단계를 둘까?"라는 열린 질문에 근거가 생겼다. 지식 자료도 실업급여 규정 위주로 다시 모으면 RAG를 다시 시험할 가치가 있다.

팀에 확인할 것 (규칙 표 vs 골든셋 정답이 다름, 규칙 표 검수 상태 not_verified):

| 항목 | 규칙 표 | 골든셋 정답 |
| --- | --- | --- |
| 65세 이상 취업특강 한도 | 모든 유형 2회까지 | 제한 없음 (P-012, P-036) |
| 반복수급자 구직활동만 인정 | 규칙 없음 (일반 8차부터만 있음) | 3차부터 구직활동만 (P-013) |

배운 점:

- **"RAG를 붙이면 좋아진다"는 가정을 측정으로 뒤집었다.** 자료에 답이 없으면 검색은 소음만 더한다. 먼저 "필요한 지식이 자료에 있는가"를 확인해야 한다.
- 운영에서 벡터 검색을 쓰게 되면 조각 임베딩은 pgvector 테이블에 둔다(실험에서는 backend/.cache 파일로 재사용).

## 7-4. 세 번째 실험 결과: 의도 분류로 규칙 카드를 필요할 때만 (2026-10-24)

RAG 실험에서 "규칙 카드를 매 턴 붙이면 서류 값 뽑기가 흐트러진다"는 걸 알았습니다. 그래서 그래프에
`classify_intent` 단계를 넣어 **활동 규정 질문(인정·증빙·한도)일 때만** 규칙 카드를 붙였습니다.

| 버전 | 질문 종류를 가리는 방법 | 1회 | 2회 | 평균 | 절차(38) | 서류(25) | 모델 호출/100문항 | 문항당 토큰 | 평균 시간 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 기준 | 규칙 카드 없음 | 68% | 71% | 69.5% | 23 / 24 | 15 / 17 | 112 | 2,757 | 1.4초 |
| (참고) D | 항상 붙임 | 68% | 69% | 68.5% | 27 / 24 | 12 / 15 | 112 | 3,983 | 1.4초 |
| **G1** | **키워드**(코드가 단어로 판단) | 73% | 69% | **71%** | 29 / 27 | 15 / 12 | 112 | 3,152 | 1.4~1.7초 |
| G2 | AI 분류(작은 호출 1번 추가) | 69% | 70% | 69.6% | 28 / 26 | 12 / 14 | 224 | 3,573 | 2.3초 |

**결정: G1(키워드 분류)을 기본값으로 쓴다 (RULE_CARDS_MODE=keyword).**

- 전체 평균은 +1.5점이라 흔들림 안이지만, **노린 질문이 꾸준히 좋아졌다**: 증빙(P-024 취업활동증명서, P-025 보낸편지함), 학원 인정(P-032). 절차 영역은 23.5 → 28문항.
- 항상 붙일 때(D)보다 토큰이 21% 적다(3,983 → 3,152). 기준 대비는 +14%.
- AI 분류(G2)는 점수가 더 낫지 않으면서 **모델 호출이 2배**, 응답이 0.9초 느리다. 키워드로 충분하다.
- 키워드는 시험 문제가 아니라 주제(인정·증빙·한도) 기준으로 정했고, 처음 버전에서 잘못 걸리던 두 가지를 일반 규칙으로 고쳤다: "실업인정"의 '인정', 파일을 건네는 말("~캡처예요", "읽어 주세요").

함께 발견한 문제 (다음에 다룰 것):

- 키워드 버전에서 꾸준히 나빠진 F-001(경력 날짜)·F-017(자격증 날짜)은 **키워드에 걸리지 않아 규칙 카드가 붙지 않은 턴**이었다. 즉 분류 탓이 아니라 **AI의 날짜 뽑기 자체가 흔들린다**. RAG 실험(K·V)에서도 F-001이 같은 식으로 흔들렸다.
- → "작년 3월", "2011년에 땄어요" 같은 날짜는 AI가 아니라 **규칙 코드로 바꾸는 것**이 결정 ②와도 맞는 다음 후보다.

설계 초안 ① 흐름의 열린 질문 "의도 분류 단계를 둘까?"의 답: **둔다.** 다만 처음에는 AI가 아니라 키워드로 충분하다(비용 0, 결과 일정).

## 7-5. 네 번째 실험 결과: 날짜는 규칙 코드가 바꾸기 (2026-10-24)

의도 분류 실험에서 "AI의 날짜 뽑기가 흔들린다"(F-001 경력 날짜, F-017 자격증 날짜)는 걸 발견했습니다.
그래서 **AI는 들은 말 그대로("작년 3월", "지난주 금요일")만 옮기고, 규칙 코드가 날짜로 바꾸는** 방식을 시험했습니다(설정 `DATE_PARSING=ai|code`).

- 이력서 연·월: 팀 공용 `resume.normalize_date`를 재사용("작년 3월" → 2025-03, 애매하면 비우고 다시 물음). 이 함수가 못 읽는 한글 달 이름("삼월")과 "올"(=올해)은 먼저 숫자로 바꿈.
- 활동 날짜("어제", "지난주 금요일", "11월 20일"): 해당 함수가 없어 `app/rules/dates.py`의 `normalize_day`로 새로 만듦.
- 자격증 취득·졸업은 연도만("2011년에")도 받고, 경력은 월까지 있어야 받음.

| 버전 | 1회 | 2회 | 평균 | 날짜 문항 통과(14문항×2회) | 서류(25) | 문항당 토큰 |
| --- | --- | --- | --- | --- | --- | --- |
| 기준 (AI가 날짜 변환) | 73% | 69% | 71% | 17 / 28 | 15 / 12 | 3,152 |
| E (첫 시도) | 66% | 67% | 66.5% | — | 12 / 13 | 3,201 |
| **E2 (보강)** | 70% | 71% | **70.9%** | **20 / 28** | **15 / 15** | 3,252 |

**결정: 날짜는 규칙 코드가 바꾼다 (DATE_PARSING=code 기본값).**

- 노린 문항 해결: F-001·F-017이 기준에선 2회 모두 실패 → E2에선 2회 모두 통과. 들쭉날쭉하던 F-002·F-005·F-011도 2회 모두 통과.
- 전체 평균은 같고(흔들림 안) 서류 영역이 안정됨. 날짜 변환이 코드라 **단위 테스트로 보장**할 수 있음(결정 ②와 같은 방향).

## 7-7. 검증 방식을 더 효율적으로 (2026-10-24)

팀 공용 키라 검증 토큰을 줄였습니다. 먼저 어디서 드는지 쟀습니다.

| 어디서 | 실행 1번당 | 발견 |
| --- | --- | --- |
| 답하는 AI의 고정 프롬프트 | 2,185토큰 × 112호출 ≈ 24.5만 | 입력의 약 80%. 그런데 **95%가 OpenAI 자동 프롬프트 캐시로 처리**되고 있었음(캐시 입력은 훨씬 쌈) |
| LLM 판정(G-Eval, gpt-4.1) | 판정 60문항 × 2호출 | 1호출은 "채점 단계 만들기"로, 같은 기준이면 매번 같은 일을 반복 |
| 실행 횟수 | 대안마다 100문항 × 2회 | 기준도 다시 돌린 적 있음 |

바꾼 것:

| 방법 | 효과 |
| --- | --- |
| 채점 단계를 `backend/.cache`에 저장해 재사용 | 판정 호출 문항당 2번 → 1번 (3문항 시험: 6 → 3) |
| `--golden-judge=off` 옵션 | 고치는 중에는 판정 없이 정답 비교만 (판정 토큰 0) |
| 보고서에 캐시 토큰·판정 토큰 표시 | 실제 비용에 가까운 숫자를 보고 판단 |
| 검증 순서: 단위 테스트 → 바뀐 영역·문항만(판정 끔) → 결정할 때 전체 1회 → 애매할 때만 2회차 | 실험당 전체 실행 2~4번 → 1~2번 |
| 기준은 저장된 보고서 재사용, 실패 문항만 `--lf`로 재실행 | 같은 실행 반복 제거 |

배운 점: **원시 토큰 수만 보면 비용을 과대평가한다.** 고정 프롬프트를 앞에 두면 캐시가 맞아 실제 비용이 크게 준다. 그래서 프롬프트 앞부분(고정)과 뒷부분(상황·대화)을 나눠 둔 지금 구조를 유지한다.

| 개인정보 보강 패턴 | 팀 pii.py에 넣어도 됨 | 내 masking.py를 지우고 pii.py로 옮김. 이제 팀원 모두의 AI가 같이 보호받음 |

**pii.py란?** 개인정보를 찾아 가리는 팀 공용 파일(`agent/input/pii.py`). 주민번호·카드·계좌·전화·이메일을 찾아 `[주민번호]` 같은 표시로 바꾸고, 주민번호·카드·계좌가 남아 있으면 외부 AI로 보내지 않게 막는 기준도 된다.

옮기면서 보안 검토가 다시 빈틈 5건을 찾아 고쳤다:

| 빈틈 | 예 | 고친 방법 |
| --- | --- | --- |
| 날짜로 시작하는 계좌가 날짜로 취급됨 | 3333-01-1234567 | 통째로 날짜(+시각)일 때만 제외 |
| 검증(생년월일·Luhn)에 떨어진 번호를 아예 안 가림 | 991399-1234567 | `[번호]`로 가림(차단 등급은 아님 → 팀 테스트 유지) |
| 이메일 안 숫자가 먼저 가려져 주소가 남음 | 800101-1234567@ex.com | 이메일을 가장 먼저 찾음 |
| 문장 끝 이름을 못 잡음 | "제 이름은 홍길동" | 문장 끝도 잡되 "몰라요"처럼 요·다로 끝나면 제외 |
| 단서 없이 따로 말한 뒷자리 | "650101 그리고 1234567" | 같은 말에 생년월일 6자리가 먼저 있으면 가림 |

또 지나치게 가리던 것도 줄였다: "월급 2500000원"(7자리 금액)은 뒷자리 단서가 있을 때만 주민번호로 본다.

반복수급자 규칙을 넣으며 발견한 것:

- 팀 규칙 표의 "구직활동만" 규칙은 한 줄만 담을 수 있어서, 여러 줄을 받도록 표 모양과 읽는 코드를 고쳤다.
- **기존 버그**: 일반 8차부터("7일마다 구직활동 1건") 내 상황 계산이 필요 건수를 0으로 읽어 "다 채웠어요"라고 잘못 말할 수 있었다 → 기간을 7일·14일씩 나눠 세도록 고침.
- 반복수급자 횟수 질문(P-014)에서 AI가 건수만 말하고 "2주마다"를 빼먹었다 → 주기를 따로 된 사실 문장으로 떼고, "횟수를 물으면 주기도 말한다"를 프롬프트에 더해 해결.

확인(새 검증 방식: 바뀐 문항만): P-012·P-013·P-014·P-036·M-005 통과, 횟수 질문 P-008·P-010·P-030 영향 없음. 단위 테스트 439개 통과.

> 골든셋을 고쳤으므로, 팀원들도 같은 골든셋으로 다시 재야 점수를 견줄 수 있다.

## 7-12. 코드래빗 리뷰 반영과 최종 재측정 (2026-10-25)

PR 4개에 코드래빗이 19건을 지적했다. 코드와 대조해 18건은 맞았고, 1건(규칙 표 행마다 출처·검수 정보)은 팀 규칙 표가 파일 머리에 검수 정보를, 행에는 근거 ID(`rule_refs`)를 두는 구조라 그대로 두었다.

가장 중요했던 지적 두 가지:

1. **같은 턴 활동 건수**: "방금 지원했는데 몇 건 남았어요?"처럼 활동 보고와 질문이 한 말에 있으면, 답은 기록 전 사실 문장으로 쓰여 건수가 하나 모자랐다. 활동 추출을 답보다 먼저 하려면 AI 호출이 2번이 되므로, **기록 뒤 건수를 규칙 코드가 문장으로 만들어 답 끝에 덧붙이는** 방식을 골랐다(결정 ②와 같은 방향, 호출은 그대로 1번).
2. **골든셋 버전이 섞인 비교**: 실험 도중 팀 결정으로 골든셋이 두 번 바뀌었는데(P-012·P-036, F-019·M-007), 79%(v2)와 gpt-5.4의 85%(v3)를 같은 시험지처럼 비교했다. 버전 표(해시 포함)를 설계 문서에 넣고, 최종 코드로 v3에서 다시 쟀다.

| 영역 | 절차 28/38 · 서류 20/25 · 근거 15/20 · **개인정보 15/15** |
| 답하는 AI | 문항당 3,639토큰(74% 캐시), 평균 1.5초, 실행 1회 약 $0.16 |

배운 점:

- **시험지가 바뀌면 점수에 버전을 붙인다.** 기대값을 고치는 건 정당해도, 고치기 전후 점수를 한 표에 섞으면 비교가 틀어진다.
- **리뷰 지적도 코드와 대조한 뒤 고친다.** 지적 하나는 팀 표 구조를 몰라서 나온 것이었다.
- 브랜치를 쌓아 올린 PR은 아래 브랜치를 고친 뒤 위로 차례로 합쳐(merge) 올린다. 같은 커밋을 위에 다시 복사(cherry-pick)하면 위 PR에 아래 변경이 또 보인다.

### 코드래빗 2차 리뷰 (2026-10-25)

1차 반영 뒤 7건이 더 달렸다. 모두 맞는 지적이었지만, **사용자에게 직접 피해가 가는 1건만 고치고** 나머지는 넘어갔다(마감 전 우선순위).

| 지적 | 처리 | 이유 |
| --- | --- | --- |
| 날짜를 못 정한 활동은 빠지는데 답은 "기록했어요"라고 말할 수 있음 | **고침**: "아직 기록하지 않았어요, 날짜를 알려 주세요" 문장을 코드가 덧붙임 | 저장된 줄 알고 실업인정을 신청하면 건수가 모자람 |
| 검색 자료 경로가 팀 수집 스크립트와 다름 | 넘어감 | 검색 기본값이 none이라 지금 동작에 영향 없음. RAG를 다시 시험할 때 고칠 것 |
| 임베딩 캐시를 조각 ID로만 비교 | 넘어감 | 실험용 캐시 |
| 같은 이름 자격증의 날짜·기관 병합 | 넘어감 | 첫 값은 저장됨 |
| 사진 off일 때도 파일을 먼저 읽음 | 넘어감 | 읽기만 하고 밖으로 보내지 않음 |
| deepeval 비공개 함수·버전 미고정 | 넘어감 | 평가 도구만 해당 |
| 예시 비용 $195 vs $183 | 넘어감 | 참고용 추정치 |

배운 점: 리뷰 지적은 "맞는가"와 "지금 고쳐야 하는가"를 따로 판단한다. 기준은 사용자 피해, 기본 설정에서 실제로 일어나는지, 고치는 비용이다.

## 7-13. 팀 설계 조합 V1 브랜치 (2026-10-26)

PR 5개(내 #214~#217, 조천산 #220)를 비교해 `feat/#176-ai-v1-combined` 브랜치에 합쳤습니다.
기준과 결과는 그 브랜치의 `docs/ai/v1/design.md`에 있습니다.

- 뼈대는 조천산 #220(실서비스 그래프·하이브리드 검색·팀 규칙표 636카드). 실제 채팅 화면에
  연결된 설계는 이것뿐이라 그래프를 이걸로 통일하고, 내 `turn_graph` 흐름은 뺐습니다.
- 내 쪽에서 가져간 것: `rules/dates.py`(조천산 `days.py`를 흡수), pii 보강, IMAGE_MODE(vision은
  call_model에서 모델 입력에만 붙여 체크포인트에 안 남김), 프롬프트 v2 원칙, 판정 캐시·비용 표,
  기록 뒤 건수(`record_activity`가 `round_after`를 돌려줌), 상황 카드(`situation_cards.py`,
  facts.round_rules로 주입).
- 뺀 것: 내 RETRIEVAL_MODE(조천산 하이브리드로 대체)·DATE_PARSING(날짜는 항상 코드가 바꿈).
- 측정(판정 끔·BM25만·파일 9문항 건너뜀 — 기존 점수들과 직접 비교 금지): 규칙 채점 통과
  68% → 프롬프트 보강·상황 카드 뒤 78%(71/91). 남은 실패는 대부분 카드 검색 miss로, 벡터
  임베딩(Upstage 키)이 있는 환경에서 재측정이 필요합니다.
- 배운 점: 구조가 다른 두 설계를 합칠 때는 "파일 머지"가 아니라 "한쪽 뼈대에 다른 쪽 부품
  이식"이 맞았습니다. 같은 이름 파일(rule_cards·retrieval)이 서로 다른 일을 해서, 역할 기준으로
  남길 쪽을 정하고 이름을 바꿔(situation_cards) 공존시켰습니다.

### `.gitignore`의 `!` 표시

```
.env            ← 무시 (안 올라감)
.env.*          ← .env.local 등도 무시
!.env.example   ← 단, 이건 예외로 올림
```

- `.env.example`은 팀원에게 필요한 설정 **키 이름만** 보여 주는 공유 견본이라 저장소에 올라갑니다. 실제 키 값은 `.env`에 넣습니다.
- 실수로 키를 커밋·푸시했다면 기록에 남으므로, 그 키를 폐기하고 새로 발급받아야 합니다.
