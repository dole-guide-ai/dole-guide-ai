# AI 엔지니어링 진행 기록 (이슈 #176, 이민수)

> 작업하면서 받은 설명과 결정, 결과를 순서대로 모은 문서입니다. 노션에 그대로 붙여 넣을 수 있게 마크다운으로 씁니다.
> 확정된 설계는 「설계 초안」 노션 페이지, 이 문서는 "왜 그렇게 했는지"의 기록입니다.

3. 설계 초안은 무엇부터 정할까
4. ③ 최소 버전 개발과 기준 점수

## 1. 전체 진행 순서

**공부 → 설계 초안(가설) → 최소 버전 개발 + 첫 평가 → 실험으로 결정 확정 → 문서 완성 + PR**

- 처음 생각한 순서는 "공부 → 질문 결정 → 개발"이었는데, 질문을 개발 전에 **다 확정하지 않는다**는 점이 다릅니다.
- 이유: 이슈가 요구하는 건 "근거 있는 선택"입니다. 개발 전에 정해 버리면 근거가 "그럴 것 같아서"뿐입니다.
  **가설 → 측정 → 결정** 순서로 가야 근거를 숫자로 댈 수 있습니다.

| 단계 | 하는 일 | 끝났다는 기준 |
| --- | --- | --- |
| ① 공부 | LLM 기본, 프롬프트, 구조화 출력, LangGraph, RAG, 평가, 보안, 우리 코드 | 확인 질문에 내 말로 답할 수 있음 |
| ② 설계 초안 | 결정 질문 7개마다 대안 + 가설 | 설계 초안 문서 |
| ③ 최소 버전 | 가장 단순한 AI로 골든셋 채점 | 기준 점수 |
| ④ 실험 | 대안을 하나씩 바꿔 점수·비용·속도 비교 | 비교표 (= 선택의 근거) |
| ⑤ 완성 | 설계 문서 확정본 + PR | PR (머지는 안 함) |

## 2. 설계 문서는 어디에 둘까

**결정: 초안은 노션에서 쓰고, 확정본은 레포(`docs/ai/`)로 옮겨 PR에 포함한다.**

| 위치 | 좋은 점 |
| --- | --- |
| 레포 | 코드와 같이 리뷰받음, 설계와 코드가 같은 커밋으로 기록됨, AI 도구가 읽을 수 있음, 평가 결과와 한곳에 |
| 노션 | 쓰기 편함, 비개발자 팀원이 보기 쉬움, 댓글 달기 쉬움 |

- 이슈는 위치를 정하지 않았으므로 둘 다 가능합니다. 섞어 쓰면 두 장점을 다 가져갑니다.

## 3. 설계 초안은 무엇부터 정할까

**0단계: AI가 맡을 일의 범위부터.** 골든셋 4개 영역(절차 안내·서류 채우기·근거 답변·개인정보 보호)이 곧 할 일 목록입니다.

**결정 질문 순서: ② 판단은 누가? → ① 흐름 → ⑤ 답 형식 → ④ 근거 찾기 → ③ 모델 → ⑥ 사진 → ⑦ 보안**

| 순서 | 질문 | 이 순서인 이유 |
| --- | --- | --- |
| 1 | ② 판단은 누가 | 모든 설계의 뼈대. 규칙 코드와 AI의 역할을 나눠야 흐름을 그릴 수 있음 |
| 2 | ① 흐름 | 역할이 정해지면 단계가 정해짐 |
| 3 | ⑤ 답 형식 | 단계 사이에 무엇을 주고받을지 |
| 4 | ④ 근거 찾기 | 자료가 조각 916개(약 2.4MB)라 통째로 못 넣음 → 검색 방식 선택 |
| 5 | ③ 모델 | 역할별로 필요한 능력이 다름 |
| 6 | ⑥ 사진 | 서류 채우기의 일부라 독립적으로 결정 가능 |
| 7 | ⑦ 보안 | 흐름이 정해져야 어디서 막을지 정함 |

질문 하나를 채우는 양식: **질문 · 대안 · 장단점 · 가설 · 검증 방법(골든셋 어느 영역, 어떤 지표)**

## 4. ③ 최소 버전 개발과 기준 점수

### 만든 흐름

`preprocess`(개인정보 가리기) → `load_context`(규칙 코드로 회차·필요 건수 계산) → `respond`(모델 한 번, JSON 답) → `apply_updates`(서류·활동 반영)

| 누가 | 하는 일 |
| --- | --- |
| 규칙 코드 (`app/rules/situation.py`) | 회차, 필요 활동 수, 인정 건수, 부족 건수, 대상기간, 활동 증빙 |
| AI (`app/agent/nodes/respond.py`) | 말 이해, 서류 값 뽑기, 답 쓰기 |

- 골든셋이 기대하는 회차·건수 값은 원래 백엔드에 계산 함수가 없었습니다(화면 쪽에서 계산). 그래서 규칙 함수로 새로 만들었고, 이것이 설계 결정 ②(계산은 규칙 코드)를 그대로 구현한 것입니다.
- 근거 검색, 사진 읽기, 최종 검사(verify)는 일부러 뺐습니다. **나중에 붙였을 때 효과를 재기 위한 기준선**이기 때문입니다.

### 기준 점수 (2026-10-24, agent=gpt-5.4-mini, judge=gpt-4.1)

| 전체 | 통과 | 실패 | 참고 실패 | 통과율(확정 문항) |
| --- | --- | --- | --- | --- |
| 100 | 44 | 54 | 2 | **45%** |

| 영역 | 통과/전체 | 주로 틀린 이유 |
| --- | --- | --- |
| 절차 | 6/38 | 답에 "1건", "12월 22일" 같은 핵심 숫자를 말하지 않음, 근거 줄 없음 |
| 서류 | 15/25 | 사진 문항 9개 전부 실패 (최소 버전은 사진을 안 읽음) |
| 근거 | 14/20 | 근거 검색이 없어 출처를 못 댐 |
| 개인정보 | 9/15 | 답 문구 판정 실패. **개인정보 누출은 0건** |

| 실패 이유 | 건수 |
| --- | --- |
| 꼭 포함할 말 누락 | 36 |
| AI 채점(judge) 기준 미달 | 30 |
| 근거 줄 없음 | 8 |
| 서류 기대값 틀림 (대부분 사진 문항) | 약 20칸 |

**핵심 발견:** 규칙 코드가 계산한 값(회차·필요 건수·인정 건수)은 기대값에서 **하나도 틀리지 않았습니다.** 결정 ②의 첫 근거입니다.
나머지 실패는 답 문구(프롬프트), 근거 검색(RAG), 사진(OCR) 쪽입니다.

## 5. 커밋·푸시·PR은 어디까지 올라가나

```
① 커밋 → ② 푸시 → ③ PR → (④ 머지)
```

| 단계 | 어디까지 | 다른 사람에게 영향 |
| --- | --- | --- |
| 커밋 | 내 컴퓨터에만 저장 | 없음 |
| 푸시 | GitHub의 **내 브랜치**(`feat/#176-ai-minsoo`) | develop·main·다른 브랜치는 그대로 |
| PR | develop에 합쳐 달라는 **요청** + 리뷰 | 리뷰·검사가 돌지만 아직 합쳐지지 않음 |
| 머지 | develop에 실제로 합쳐짐 | 이슈 조건이 "PR까지"라 하지 않음 |

- 실험할 때마다 커밋·푸시하면 "무엇을 바꿨더니 점수가 어떻게 됐다"가 기록으로 남습니다.

## 6. 보안 검토 지적과 수정

커밋 후 자동 보안 검토가 개인정보 가리기(마스킹)의 빈틈을 세 번 찾았고 모두 고쳤습니다.

| 지적 | 예 | 수정 |
| --- | --- | --- |
| 붙여 쓴 주민번호 | `6501011234567` | 구분자 없이 13자리도 가림 |
| 한글에 붙은 번호 | `계좌110-234-567890이에요` | 숫자 경계를 `\b`(단어 경계) 대신 "앞뒤가 숫자가 아님"으로 판단 |
| 점·공백 구분 | `010.1234.5678`, `1234 5678 1234 5678` | 구분자로 공백·점·하이픈 허용 |
| 띄운 하이픈 | `110 - 234 - 567890` | 숫자 사이 구분자를 3글자까지 허용 |

- 10자리 미만 숫자는 가리지 않습니다. 국내 계좌가 10~14자리이고, 짧은 숫자까지 가리면 날짜·금액이 잘못 가려지기 때문입니다.
- 배운 점: 정규식 `\b`는 한글도 "글자"로 보기 때문에, 한글에 붙은 숫자 앞에서는 경계가 생기지 않습니다.

## 7. ④ 실험은 무엇부터 할까

**결정: 프롬프트 → 근거 검색(RAG) → 사진(OCR) → 모델 비교**

| 판단 기준 | 질문 |
| --- | --- |
| 효과 | 몇 문항을 고칠 수 있나 |
| 비용 | 새로 만들 게 얼마나 많나 |
| 의존성 | 다른 실험 결과에 영향을 주나 |
| 측정 | 효과를 깔끔하게 잴 수 있나 |

- **프롬프트가 1번인 이유:** 실패의 대부분이 답 문구이고, 고치기 가장 싸며(한 번 실행에 약 5분), 모든 실험의 바탕이라 먼저 고정해야 다음 실험의 효과를 구분할 수 있습니다.
- **모델 비교가 마지막인 이유:** 설정값만 바꾸면 되지만, 프롬프트·검색이 정해진 뒤에 재야 공정합니다.
- **주의:** 시험 문제에 맞춰 답을 외우게 하면(예: "12월 22일을 말해라") 점수만 오르고 실력은 그대로입니다. "상황의 숫자는 답에 반드시 넣어라"처럼 **일반 원칙**으로 고쳐야 근거로 인정받습니다.
- **주의:** AI는 같은 질문에도 답이 조금씩 달라서, 2~3점 차이는 우연일 수 있습니다. 중요한 비교는 2번씩 돌려 흔들림 폭을 함께 적습니다.

## 7-1. 첫 실험 결과: 프롬프트 (2026-10-24)

비교한 세 가지 (모두 gpt-5.4-mini, 채점 gpt-4.1, 버전마다 2회 실행):

| 버전 | 바꾼 것 | 1회 | 2회 | 평균 | 흔들림 | 절차(38) | 문항당 토큰 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 기준 | 최소 버전 | 45% | 38% | 41.5% | 7점 | 6 / 5 | 1,764 |
| A | 프롬프트 v2: 숫자는 "N건"·"M월 D일"로 직접, 근거 줄, 거절 원칙, 결론부터 | 55% | 63% | 59% | 8점 | 13 / 18 | 2,444 |
| B | A + 규칙 코드가 출처 달린 사실 문장을 만들어 AI가 그대로 옮김 | 63% | 62% | **62.5%** | **1점** | **21 / 22** | 2,733 |

**결정: B 채택.**

- 기준 → A(+17.5점)는 흔들림보다 훨씬 커서 확실한 개선입니다. 지시문만 바꿔도 효과가 큽니다.
- A → B는 전체로는 +3.5점이라 흔들림 안입니다(우연일 수 있음). 하지만 **숫자·날짜를 말해야 하는 절차 영역이 확실히 좋아졌고**, **흔들림이 8점 → 1점**으로 줄었습니다.
- 행정 안내는 매번 같은 답을 주는 것이 중요하므로 안정성을 근거로 B를 고릅니다. 토큰은 12% 늘지만 문항당 약 300토큰이라 부담이 작습니다.
- 결정 ②(계산은 규칙 코드)를 **문장 단계까지** 적용한 것이 맞다는 근거입니다.

배운 점:

- **같은 코드도 점수가 7점 흔들린다.** 그래서 대안마다 2회씩 돌려 평균과 흔들림을 함께 봐야 합니다. 차이가 흔들림보다 작으면 "좋아졌다"고 말하지 않습니다.
- **문항에 맞춘 문구를 넣지 않는다.** "12월 22일을 말해라"가 아니라 "상황의 숫자는 답에 직접 써라" 같은 원칙만 넣어야 점수가 실력을 보여 줍니다.
- 비용 비교를 위해 골든셋 보고서에 모델 호출 수·토큰·시간 집계를 추가했습니다(판정 모델은 제외).

develop 최신화 (2026-10-24):

- develop을 합치니 필요 건수 계산이 팀의 활동 규칙 표(`data/rules/activities.json`)로 옮겨져 있어, 제 코드도 그 표를 읽게 바꿨습니다. 표에 없는 유형(반복수급자)은 "계산할 수 없으니 센터에 확인"으로 안내합니다(이전엔 "다 채웠어요"로 잘못 말할 수 있었음).
- 합친 뒤 골든셋 62%로 B와 같은 수준을 확인했습니다.
- develop에 팀원의 개인정보 가리기(`agent/input/pii.py`)와 회차 점검(`rules/rounds.py`)이 들어와 제 코드와 겹칩니다. 정리 대상입니다.
- 실험이 도는 중에는 develop을 합치지 않았습니다. 중간에 코드가 바뀌면 2회차 실행이 다른 코드로 돌아 비교가 오염되기 때문입니다.

## 7-2. 팀원 코드와 겹치는 부분 정리 (2026-10-24)

develop에 팀원이 만든 공용 코드가 들어와 제 코드와 겹쳤습니다. 같은 일을 두 곳에서 하면 규칙이 바뀔 때 한쪽만 고쳐지는 위험이 있어, 팀 코드를 쓰도록 바꿨습니다.

| 하는 일 | 바꾸기 전 (내 코드) | 바꾼 뒤 |
| --- | --- | --- |
| 개인정보 가리기 | `agent/masking.py`에 모든 패턴 | 팀 `agent/input/pii.py`(생년월일 검증·카드 Luhn 검사·외부 전송 차단)를 먼저 쓰고, **pii가 놓치는 경우만** 보강 |
| 회차 점검 (같은 날 1건, 기간 밖) | `situation.py`에 직접 계산 | 팀 `rules/rounds.py`의 `check_round` (허용 종류·누적 한도·주 단위까지 포함) |
| 활동 종류 이름·필요 증빙 | `situation.py`에 임시 표 | 팀 활동 규칙 표 `rules/activity_table.py` (`data/rules/activities.json`) |
| 같은 날 1건 사실 문장 | 날짜를 직접 세서 만듦 | 회차 점검의 경고 문구를 그대로 사용 |

pii.py가 놓쳐서 내 코드에 남긴 보강 (이전 보안 검토에서 막은 경우):

| 사례 | 예 |
| --- | --- |
| 주민번호 뒷자리만 말함 (골든셋 M-005) | "뒷자리는 1234567" |
| 점으로 구분한 주민번호 | 650101.1234567 |
| 구분자 없거나 공백·밑줄·슬래시·띄운 하이픈으로 쓴 계좌·카드 번호 | 11023456789012, 110 - 234 - 567890 |
| 자기소개 말투의 이름 | "제 이름은 홍길동이에요" |
| 한글이 섞인 이메일 (정리 직후 보안 검토가 찾은 회귀) | 홍길동@회사.한국 |

→ 이 보강은 팀 pii.py에 넣는 게 맞습니다. pii.py 담당 팀원과 상의할 거리로 남겨 둡니다.

결과 (gpt-5.4-mini, 2회):

## 8. 부록: 함께 알게 된 개발 상식

### `.gitignore`의 `!` 표시

```
.env            ← 무시 (안 올라감)
.env.*          ← .env.local 등도 무시
!.env.example   ← 단, 이건 예외로 올림
```

- `.env.example`은 팀원에게 필요한 설정 **키 이름만** 보여 주는 공유 견본이라 저장소에 올라갑니다. 실제 키 값은 `.env`에 넣습니다.
- 실수로 키를 커밋·푸시했다면 기록에 남으므로, 그 키를 폐기하고 새로 발급받아야 합니다.
